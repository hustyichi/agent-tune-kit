# 修改候选与实际验证的可读性诊断

核对日期：2026-11-10（Asia/Shanghai）。源码基线：`48e16bc`，包版本 `2.3.1`。范围为用户指定的本地 Trace 预览中 ISSUE-003 的修改候选、两次验证及对应 ATK 实现。本文记录诊断，不代表已修复或业务验收。

## 结论

两个阶段尚未形成面向读者的说明结构：存储侧主要约束版本、证据和执行状态，展示侧复用通用 JSON 卡片，未把修改内容、验证方法和效果边界组织成可读正文。此外，证据索引存在可复现的回归，导致已有的 diff、检查记录和验证材料无法从页面打开。

源记录并非没有信息；页面也不是旧脚本。仅调整样式、翻译字段或重新生成 HTML，不能完整解决这些问题。

## 已确认的原因

### 1. 修改卡片优先显示候选身份，遗漏已有说明

[`app.js:173`](../agent_tune_kit/visualize/assets/trace/app.js#L173) 的 `recordCard()` 同时处理修改和验证。对象记录默认只显示 `status`、`target_issues`、`candidate_loaded`、`candidate`、`execution`、`conclusions`、`limitations`，其他字段进入折叠的完整 JSON。调用者直接用归档路径作为标题（同文件第 351、358 行）。

样本的 change 已保存中文 `proposal`、实际 patch、六项本地检查和 `remaining_verification`。默认修改卡片却只呈现状态和 commit、bundle 哈希等候选身份信息。读者必须展开 JSON 或追查 patch 才能理解修复意图与实际变更。`proposal` 只是已选方案，也不能替代按实际 diff 编写的完成说明。

以页面内的真实记录调用当前 `recordCard()`，用最小元素替身收集未折叠文字，确认非空 `proposal` 不在默认正文中。页面内嵌脚本与当前源码全文一致；这不是旧页面缓存造成的差异。

### 2. 验证卡片原样倾倒执行对象，缺少方法和范围的摘要

[`app.js:185`](../agent_tune_kit/visualize/assets/trace/app.js#L185) 先显示候选身份，再通过 `section("实际执行", content.execution)` 把整个执行对象变成 JSON `<pre>`，之后才显示结论。`section()` 本身只调用 `pre()`，不解释验证设计。

样本的 `execution` 同时包含方法、模型、命令、历史输入引用、加载证明、判定标准、观测和汇总计数。这些字段没有转换为“验证什么 → 怎样对照 → 观察到什么 → 能证明什么”的结构。两份卡片的默认正文约为 4,235 和 4,844 个字符，结论理由分别位于约第 3,967 和 4,531 个字符之后。该数字是函数输出的文字顺序，不是浏览器像素测量；CSS 会限制 `<pre>` 高度并产生内部滚动。

还有三个加重理解成本的细节：

- [`progressOf()`](../agent_tune_kit/visualize/assets/trace/app.js#L45) 只要发现 verification 条目就标记“已验证”，不检查是否仍在运行或结论是否为 `inconclusive`。这不是记录被改成通过，但标签没有体现执行与效果的区别。
- [`trace.py:164`](../agent_tune_kit/visualize/trace.py#L164) 按验证目录名排序，ID 为随机标识时不保证时间顺序。当前样本恰好把后一次聚合验证放在前面，页面没有解释它包含前一次样本；不能将两份记录当作独立总体重复计数。
- `recordCard()` 递归收集整个包装对象的引用；修改包装内包含全部 verifications，因此修改页也混入验证材料按钮。`{path, sha256}` 的候选制品身份也被当作会话内证据，缺少用途区分。

### 3. 证据按钮与证据索引的范围不一致，形成实际断链

[`app.js:161`](../agent_tune_kit/visualize/assets/trace/app.js#L161) 为处理记录中递归找到的引用生成按钮。点击时只查询 `data.references`；未收录的引用进入“此引用没有可用的归档预览”分支（第 155–159 行）。

但 [`trace.py:185`](../agent_tune_kit/visualize/trace.py#L185) 目前只为 detection、Issue 的 evidence 和 segments 建立索引，没有收集 change 和 verification 的引用。样本中以下七份材料的哈希有效、`query.show()` 可读取，却全部不在页面索引中：

- 候选 patch、本地检查记录；
- 初次验证脚本和结果；
- 追加验证脚本、结果和评估记录。

页面 `warnings` 仍为 `[]`，因为遗漏的引用根本没有进入校验循环。

Git 将这处范围缩减定位到 `886773f66d1353932fdfbb22edd6ad531d001de8`（2026-11-08）：原来的 `_references([session["detections"], issues])` 被换成只遍历 `all_issue_refs(item)`。片段关联所需的引用子集同时被用于全页面材料索引，候选和验证材料因此被漏掉。

在临时合成归档中，只保留一个 Issue、一个诊断、一个候选 patch，就能复现：patch 可读、索引缺失、无警告。仅在内存中恢复完整处理记录的引用遍历，patch 正文立即进入索引，验证了因果关系。这个探针不是最终修复：正式实现还须区分会话证据和外部制品身份，保留路径、哈希及容量校验。

### 4. 生产契约和测试只保证部分完整性，没有保证可读性

[`save_change()`](../agent_tune_kit/traces/records.py#L443) 要求完成记录具有 candidate 和 diff，但没有要求实际修改的可读说明。[`save_verification()`](../agent_tune_kit/traces/records.py#L489) 接受自由结构的 execution 对象，并要求逐问题结论及必要加载证据；它没有统一的验证方法、对照方式与观测摘要展示契约。

[`atk-trace-optimize`](../skills/atk-trace-optimize/SKILL.md#L24) 和 [`atk-trace-verify`](../skills/atk-trace-verify/SKILL.md#L24) 要求保存真实变更、执行及证据，并在对话中交付说明，但没有要求把同样清晰的说明持久化为这两个页面阶段的正文。该缺口允许“记录足够追溯、页面仍难理解”的合法产物。这里是设计层面的归因，不把每个自由字段都判为错误。

现有 [`test_all_issue_stages_and_shared_change_show_each_verification`](../tests/test_visualize_trace.py#L170) 检查记录数量、共享关系、结果保存和归档不变，没有检查默认正文能否解释改动、效果边界或 change/verification 材料是否可打开。其 `VER-001`、`VER-002` 命名也未暴露随机 ID 排序问题。

## 样本中实际修改与验证的含义

下面是根据已保存 patch、检查记录、执行脚本和评估记录整理的阅读对照，未重新执行业务验证，也未独立重新判定每个模型提案。

**实际修改：**候选在运行时工程清单提示中补充规则：准备工程返回经过验证的绝对根，但不会改变 shell 当前目录；读取工程文件时使用该根下的绝对路径，或每次先进入该根再使用相对路径；不能依赖前一次 Bash 留下的目录。同时增加测试，检查这些规则确实进入最终系统提示。冻结 patch 只涉及提示生成文件及其测试文件；它不是自动纠正 shell 工作目录的运行时实现。

**本地检查：**记录了一次预期失败、修改后 155 项通过/1 项跳过，以及类型检查、构建、产物提示文本和差异检查通过。它们支持提示注入与局部工程检查通过，不能单独证明 Agent 的两次实际读取已成功。

**模型验证：**从两个历史失败前的检查点提取上下文，对同名模型进行单步 A/B；候选只增加被冻结的提示文字。第一次每个检查点执行一对，第二次各追加两对，合计三个配对样本/检查点、12 次模型调用。加载证明针对送给模型的候选文字，不是线上部署加载证明。

| 归档判定：首次工具提案正确定位目标 | 对照 | 候选 |
| --- | --- | --- |
| 词条读取检查点 | 0/3 | 1/3 |
| Schema 读取检查点 | 2/3 | 3/3 |

这里只观察模型提出的下一步工具调用；没有启动完整 SDK Agent、恢复历史工程或执行生成的 Bash。记录显示有限的路径选择改善，但未观察到真实首次读取成功及重试次数，所以两份效果结论均为 `inconclusive`。这些事实应在页面主阅读区域直接表达。

## 最小修复范围与验收建议

方案修订：2026-11-10。用户明确要求候选修改简要说明实际修改、基于根因的修改原因和待验证内容；可关联修改文件。页面不展示完整 diff、候选版本、哈希或原始 JSON，也不提供这些内容的折叠区。完整资料继续保留在本地归档。以下替代先前“折叠技术记录”的建议。现已按用户授权实现，实施核验及尚未完成的视觉验收见[验证记录](trace-tuning-validation.md#concise-change-and-verification-views-2026-11-10)；下方“本次核验与限制”保留初次诊断时的历史口径。

### 页面内容

候选修改固定回答三个问题：

1. **修改了什么：**按实际行为变化归并修改项，每项一到两句，可在该项旁关联文件。只描述已完成的修改，方案中的未实施部分不能写成事实。
2. **为什么修改：**与修改项逐项对应，说明诊断中的哪个原因或机制缺口需要该改动，以及预期怎样改善。根因尚有不确定性时保留限定，不复制整段诊断。
3. **待验证内容：**列出尚需观察的具体行为和成功条件，不把本地检查通过写成 Agent 效果已确认。后续是否得到验证由验证记录表达，不因展示需要改写冻结候选。

实际验证沿用简洁原则，建议只呈现**如何验证、观察结果、结论与局限**。方法说明真实执行范围、必要对照与样本口径；结果保留关键数字与观察对象；结论使用已保存的逐问题结论，并明确尚未覆盖的范围。运行完成和效果通过分别表达。追加验证说明新增样本与累计样本的关系。

以当前样本为例，候选页正文可写为：

> **修改了什么**：在运行时提示中补充工程文件读取规则：使用经过验证的绝对工程根，不依赖前一次 Bash 目录；增加检查最终提示确实包含该规则的测试。
>
> **为什么修改**：运行时清单主要强调写入定位，而准备工程不会切换 shell 目录；补充读取规则以减少相对路径落到错误目录的风险。
>
> **待验证内容**：在完整 Agent 回放中确认两处目标文件均首次读取成功，无需因路径错误重试。

文件名可紧邻对应修改项显示为链接。局部检查的必要结果放入验证说明，不在候选页另铺一组检查命令和日志。页面不再生成遍历整个记录得到的材料按钮列表。

### 生成与实现

采用少量有明确含义的摘要字段：修改项逐项绑定“实际变化、根因理由、相关文件”，待验证内容单独保存。由 optimize 在读过实际 diff 与采用的诊断后提炼写入；verify 按实际执行和输出写入简短方法与观察说明。现有结构化结论继续作为效果状态的权威来源。

写作约束是每条围绕一个事实或因果关系，用短句概括；保留影响判断的条件、否定和样本分母。避免整段拷贝 Prompt、代码、诊断、命令或 JSON；不以字符截断代替摘要，也不由浏览器在显示时猜测因果。

| 范围 | 应达到的结果 |
| --- | --- |
| `skills/atk-trace-optimize/SKILL.md`、`skills/atk-trace-verify/SKILL.md`、`docs/trace-tuning.md` | 规定上述摘要内容及写作要求，保存到原记录；逐项核对实际改动与根因，执行事实与结论。 |

| `visualize/assets/trace/app.js` | 修改与验证各用专用呈现，移除这两页的技术元数据、原始 JSON、diff 展示及递归材料按钮；明确效果结论与执行状态。 |

实施顺序：先统一摘要契约和 Skill 生成要求，再替换两页呈现并清理不再需要的按钮，最后核对保留的链接、状态、旧记录兼容与真实样本。正文清晰程度需人工阅读验收，自动测试只验证结构、引用与已定义行为。

核心验收问题：读者能否通过短正文准确说明“改了什么、为什么针对这个根因、还要验证什么”，并在实际验证页理解“执行了什么、观察到什么、结论证明到哪一步”。
