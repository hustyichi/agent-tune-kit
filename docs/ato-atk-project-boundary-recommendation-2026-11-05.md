# ATO 与 ATK 的项目边界选型建议

日期：2026-11-05（Asia/Shanghai）。性质：选型分析与建议，尚未成为用户确认的架构决策。本次不迁移代码、不改变分发范围、不建立新的运行依赖。

## 1. 建议

**现阶段保留 ATO 独立仓库、独立包，将它定位为与 ATK 协同的可选轨迹调优工具；先打通实际使用流程，再根据共同发布与维护需求决定是否合仓。**

ATO 负责从真实会话发现问题、调查根因、记录修复和验证；ATK 负责将有明确输入和验收依据的问题纳入数据集，执行更广范围的回归并比较结果。两者形成一个产品使用闭环，但无需立即搬到同一仓库。

这一建议基于当前已有实现与分发约定，不是认为轨迹调优不属于 ATK，也不是认为不同领域模型必须分仓。如果未来明确把 ATO 作为 ATK 面向同一批用户交付的通用能力，并且源码可见性和分发约定兼容，**同仓、分模块、保留两条工作流**会更适合长期维护。

## 3. 两种方案的优劣势

这里将“放在 ATK 统一维护”按合理实现理解：同仓维护两个独立领域模块，可以分别构建包；不预设必须合并命令、目录、版本号和全部流程。

| 比较维度 | ATO 独立项目，与 ATK 衔接 | 放入 ATK，同仓分模块 |
| --- | --- | --- |
| 当前落地成本 | 保留已有 CLI、包、历史目录；主要新增必要桥接和验收 | 在桥接之外还需迁移源码、测试、文档、构建与插件载荷，处理旧入口兼容 |
| 使用体验 | 两套安装和阶段入口，用户需要理解交接位置 | 更容易统一发现、安装、文档和导航；仅搬代码不会自动获得这些收益 |
| 维护效率 | 两套安装、版本、发布和文档需要分别维护；交叉变化需验证版本配对 | 同一改动可同时修改双方契约与测试；适合同一维护者长期频繁联动 |
| 领域演进 | ATO 可围绕长会话、问题调查和动态验证独立迭代 | 同样可以保持独立模型，但容易因“统一”将 CSV、固定阶段或评分前提施加给轨迹调查 |
| 共用代码 | 通过明确接口复用；过早独立公共库会形成第三个维护对象 | 更方便提取真正相同的安装、文件和展示能力；相似功能仍需核对语义，不能直接合并 |
| 分发与依赖 | 自然保留内部 ATO 与对外 ATK 的既有边界 | 技术上可分包，但要显式隔离构建输入、版本与插件资源；同仓源码可见性也需兼容 |
| 变更影响 | ATO 试验通常不触及 ATK 发布与现有用户 | 公共设施改动需同时验证两种使用方式；分模块能缓解，不能消除 |
| 接入与复用 | 未使用 ATK、没有数据集的目标项目也可独立使用 ATO | 可通过独立入口保持相同能力；若强制先初始化评测集，会提高采用门槛 |
| 长期产品方向 | 易形成两个产品和重复路线图，需要明确职责与交接 | 更适合一个完整调优产品，新增能力更容易被现有 ATK 用户发现 |

**独立方案真正的代价**是持续维护两套产品入口、版本配对和重复基础设施；不是“拆开就天然解耦”。**同仓方案真正的优势**是联动变更和用户交付更集中；不是“放进同一个目录就能复用所有能力”。

同一仓库可以维护独立 Python 包，并按包构建，因而“内部 wheel 与 PyPI 包不同”不是技术上必须分仓的证明。它是本次迁移需要额外处理的已确认交付约束。参考 [uv workspaces](https://docs.astral.sh/uv/concepts/projects/workspaces/) 与 [按包构建](https://docs.astral.sh/uv/guides/package/)。

## 4. 为什么当前选独立协同

1. **两种方案都必须支付语义衔接成本。** 把源码放在 ATK 下，并不会补齐历史会话的可执行输入、期望行为、环境恢复和样本映射。ATK 当前诊断入口需要含 `atk_id`、`agent_output` 的评测结果，evidence-only 不可评分。迁仓无法替代这部分设计。
2. **当前分发约定明确不同，统一发布意图尚未确认。** ATK 的 `pyproject.toml` 会整体打包 `skills/`、`templates/` 和 `docs/`。若把内部 ATO 直接放入这些目录，就会改变实际分发内容。可通过同仓多包解决，但新增的构建隔离暂时不带来轨迹调优能力。
3. **当下验收重点是证明实际问题能被完整修复和验证。** ATO 已有的实现足以继续开展真实闭环验收；现在同时迁仓，会把安装、兼容和领域流程变化混在一起，增加定位成本。保留已有实现是为了减少新增变量，不是把沉没成本当作永久分仓理由。
4. **可确定的重用点少于表面上的重合。** 两边都有证据、报告和状态，但一个服务于单问题调查与候选验证，一个服务于样本判定与版本比较。先复用 ATK 已有评测和证据入口，比立即抽取公共框架更直接。

此判断假定仍由当前维护者推进、ATO 首版内部交付约定仍有效，且目前目标是扩展实际调优能力。若目标变成一个统一对外交付的 ATK 产品，应重新评估维护边界，不把本建议固定为长期规则。

## 5. 怎样让独立 ATO 真正扩展 ATK

建议的交接关系如下；这是待实现方向，不表示已有自动互通：

```mermaid
flowchart LR
    T[真实会话与本地轨迹] --> A[ATO：发现问题、调查、修复与验证]
    A --> C[选定问题：补齐输入、验收依据与来源]
    C --> K[ATK：回归样本、评测和版本比较]
    K --> R[回归结论关联回原 issue 与候选]
```

第一轮只需围绕一个实际问题验证交接：

- **ATO 保持自身流程。** 没有 ATK 数据集也能采集、分析和局部验证；原始快照、issue、attempt 与 run 继续归 `.ato/` 管理。
- **满足条件后再形成回归样本。** 交接包含具体目标、可执行输入或准备线索、可信验收依据、来源快照/issue 标识，以及候选提交和验证范围。会话不一定对应一行，必须显式确定拆分及执行映射；不得把历史 Agent 输出自动当作正确答案。
- **按需要利用已有 ATK 能力。** 只需查看证据时，可实现受信任的本地 importer，复用现有 `import-evidence`。要进入评分流程，则准备真实结果映射或由 ATK 重新执行，继续使用现有 dataset、runner、judgments 和 report。当前没有已验证的 ATO 专用适配器，不能承诺直接导入即用。
- **分别保留结论的权威位置。** ATO run 回答本次候选在什么范围内有效；ATK judgments/report 回答哪些样本通过、是否发生回归。双方保存来源与结果引用，不互相覆盖结论，不创建第三套评分记录。独立交接必要证据时保存受控副本和摘要，避免只引用会变化或丢失的外部文件。
- **保持身份和版本可核验。** 快照、issue、attempt、run 与 `atk_id`/评测版本显式关联；历史会话与新回放分别记录。原始修复问题与独立保护样本区分，局部修复验证不能冒充全量改善。

导入时还有一个现有约束：ATK 不支持同一来源封存后的材料补写，来源内容变化会被拒绝。因此桥接应按不可变快照或回放 run 分配稳定的 `source_run_id`，不能只用 session ID 识别该会话历次变化的全部材料。来源不变时复用导入结果，来源不同则显式创建新的导入对象。[导入实现](../agent_tune_kit/results/evidence.py)

Langfuse 官方也区分 trace/session 与 dataset，并支持从生产轨迹挑选样本、补充期望结果、记录 source trace/observation ID。这支持上述显式交接思路，不能证明本地已完成接入。[数据模型](https://langfuse.com/docs/observability/data-model)、[Datasets](https://langfuse.com/docs/evaluation/experiments/datasets)。

首轮不需要统一所有事件格式、复制第二套回放引擎、迁移历史 `.ato/`/`.atk/`、增加通用插件框架或抽取公共 SDK。既有数据格式和读写边界保持清楚后，再根据真实重复工作提取公共能力。

## 6. 何时改选同仓维护

满足以下方向后，同仓方案的收益会明显增加：

- 产品定位明确为同一批用户使用的一个 ATK 调优套件，统一安装与发现是实际需求。
- ATO 源码与插件资源的可见性、内部交付约定和 ATK 分发方式已明确兼容；不靠目录名或未启用的命令控制分发。
- 实际开发频繁需要同时改两边，跨仓版本配对与重复维护已成为持续成本，而不只是预想。

届时建议迁入 ATK 的独立 trace/ATO 模块或包，保留现有 `ato` 入口与 `.ato/` 数据读取能力，维持 dataset/eval 和 session/issue 两条工作流；分发策略按需要选一包或多包。先保证安装、旧数据和端到端交接兼容，再删除确实重复的基础设施。无需一开始把全部功能塞入 `atk eval`，也无需为了合仓重写现有 ATO。

未重新运行模型、企业网关、真实 Agent 闭环或完整测试套件；本报告引用的既有验证保持原日期和原范围。未量化迁移工期或性能收益，因为没有对应测量。需要用户最终决定的是长期产品与交付定位；本建议不是公开分发、迁移代码或修改已有产品决策的授权。
