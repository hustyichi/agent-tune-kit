## 1. 目标与范围

单会话预览 `preview.html` 一次只能看一个会话。大盘在一个项目内汇总全部会话，回答两类问题：

- **会话维度**：项目里有哪些会话，各有多少问题，处理到哪一步，哪些需要关注。
- **异常维度**：哪些同类异常在多个会话中反复出现，整体处理到哪一步。

大盘只负责“看全局、选目标”。点击后跳到对应会话的预览查看泳道、片段和证据，不重复实现单会话页已有的能力。视觉风格与单会话页一致，两个页面看起来属于同一个工具。

本期不做：跨 Agent 项目汇总；按分类共享诊断、修复或验证；会话发生时间与趋势；分页或密度切换；页面内编辑。

## 4. 数据契约

### 4.1 项目级分类表 `.atk/traces/categories.json`

```json
{
  "schema_version": 1,
  "revision": 3,
  "categories": [
    {
      "id": "shell-arg-retry",
      "name": "Shell 路径/参数传递导致反复重试",
      "definition": "工具调用因相对路径、stdin 或变量未展开失败并重试；不含业务逻辑错误",
      "deprecated": false,
      "created_at": "2026-11-10T10:00:00+08:00",
      "updated_at": "2026-11-10T10:00:00+08:00"
    }
  ]
}
```

- `id` 使用 kebab-case，创建后不变。`name` 和 `definition` 可以修订；`definition` 必须写清与相近分类的边界。
- 条目不删除。不再使用的分类标为 `deprecated: true`，已引用它的 Issue 仍正常显示；新写入的 Issue 不能引用已弃用分类。
- 文件放在私有归档内，跟随 `.atk/traces/` 一起被 Git 忽略。写入使用原子写和文件锁，与现有 `session_write_lock` 的做法一致。

| 命令 | 作用 |
| --- | --- |
| `atk trace category --list [--project-root] --json` | 列出分类表，以及每个分类在各会话中被引用的次数，供检测时复用 |
| `atk trace category --data FILE [--project-root] --json` | 新增或修订一条分类；修订时须带上分类表当前的 `revision`，防止覆盖并发写入 |

`trace category` 不绑定会话，所以不带 `--session-id`，在 `cli/trace.py` 中单独注册。

### 4.2 Issue 可选字段 `category`

- 取值必须是分类表中未弃用的 `id`，由 `prepare_issue()` 校验。字段缺省即“未分类”，旧记录不用迁移。
- 通过现有 `atk trace issue` 写入，规则与 `selection_reason` 相同：修改时产生新 revision，旧值写入 `history`；更新时省略该字段则保留原值。
- `save_diagnosis()` 的 Issue 快照在字段存在时带上 `category`。

### 4.3 检测时归入分类（`atk-trace-detect`）

1. 保存 Issue 之前运行 `atk trace category --list --json`。
2. 为每个保留的 Issue 选一个已有分类；确实没有合适的才新建，并写清 `definition`。
3. 当前会话中已有但未分类的 Issue，本次检测一并补上：只改 `category`，不改标题、描述和片段。
4. 不修改其他会话的 Issue。
5. 交付摘要列出本次新建的分类及其包含的 Issue，方便用户事后要求合并或改名。

分类的语义由宿主判断，CLI 只校验结构和引用，沿用“CLI 校验、宿主判断”的分工。

## 5. 实际进度口径（两个页面共用）

新增 `agent_tune_kit/traces/progress.py`，根据 Issue 及其改动和验证记录计算进度。函数不做 I/O，`build_trace_data()` 和大盘数据构建都调用它，并把结果写入页面数据。`app.js` 的 `progressOf()` 改为直接读取这个结果。

按下表从上到下取第一个满足的条件：

| 进度 | 判定 | 颜色 |
| --- | --- | --- |
| 已排除 | `status` 为 `excluded`（唯一参考声明状态的地方） | 浅灰 `#dce4ea` |
| 验证通过 / 验证失败 / 无法判断 | 存在已结束的验证时，取最近一次已结束验证中该 Issue 的 `outcome` | 绿 `#2f8f5b` / 红（新增）/ 琥珀（新增） |
| 验证中 | 最近一次验证为 `running` | 蓝 `#3f7cac` |
| 待验证 | 改动已完成，没有验证记录 | 蓝 `#3f7cac` |
| 修复中 | 存在 `running` 状态的改动 | 蓝 `#3f7cac` |
| 已诊断 | 有诊断，没有改动 | 橙 `#d8892f` |
| 待诊断 | 没有诊断 | 灰 `#b7c4ce` |

- 绿、蓝、橙、灰沿用单会话页 `.progress-dot` 已有的颜色。红和琥珀为新增色，饱和度与现有颜色保持一致，并加入共享的颜色变量。
- “最近一次”沿用 `_record_time()` 的规则：按 `created_at` 排序，时间缺失或不带时区的排在最后，相同时按 ID。大盘的时间统一换算为 `Asia/Shanghai` 显示。
- 共享改动按每个目标 Issue 各自的验证结论计算；非所有者 Issue 通过所有者路径读取。
- 失败和中断的验证尝试仍保留在会话页，不影响“最近一次”的取法。“已结束”指 `completed` 或 `partial`；已有结束的验证时，之后仍在进行或中途停止的复验不覆盖已有结论。
- 多次改动时（实现时补充，2026-11-10）：上表作用于最新一次已完成或进行中的改动。新改动的进度取代旧改动已有的验证结论，因为旧结论不能说明新候选的效果。
- 最新改动下存在无法读取的验证记录时记为“无法判断”，不退回更早的结论；两个页面按同一方式读取验证记录。

对照数据（2026-11-10 对 Magic 6 个会话只读统计）：37 个问题中，待诊断 14、已诊断 22、无法判断 1。最后这个是 cb27cb0f 的 ISSUE-003，两次验证都是 `inconclusive`，在单会话页上会从“已验证”改为“无法判断”。

- 分类卡片：分类名、一行定义（超出截断）、会话数与问题数、最近出现时间、进度条。已弃用的分类加“已弃用”标记，排在正常分类之后。
- 排序：按涉及的会话数倒序，相同时依次按问题数、最近出现时间。
- “未分类”是最后一条通栏，不与正常分类混排。

点击分类卡片打开**分类抽屉**：完整定义，问题列表按会话分组。组头为缩短的 Session ID 和“打开会话页”，每行为进度点、编号、标题、进度、↗ 跳转。

### 7.4 跳转与深链

| 动作 | 目标 |
| --- | --- |
| 问题行 ↗ | `./<会话目录>/preview.html#issue=ISSUE-008`（沿用单会话页已有的 hash 格式） |
| 打开会话页 | `./<会话目录>/preview.html` |
| 单会话页顶栏“← 大盘” | `../index.html#view=session&session=<id>`，只在大盘存在时显示 |
| 单会话页问题卡片上的分类标签 | `../index.html#view=category&category=<id>` |
| 大盘深链 | `#view=session&session=…`、`#view=category&category=…`，打开后定位并展开抽屉 |

会话目录名使用归档中的实际目录名（含转义），与 `archive.component` 一致。

### 7.5 提醒与异常

- **预览需刷新**：`preview.html` 不存在，或其修改时间早于该会话最近一次记录写入。
- **记录读取失败**：会话或某个 Issue 读取失败时，只在对应卡片或行显示原因，其他内容正常显示。
- **大盘过期**：页面显示生成时间；文件更新后，已打开的页面需要刷新浏览器。

### 7.6 规模

卡片网格按约 320px 一列自适应。本期依靠搜索、进度筛选和排序应对几十个会话；到几百个会话时再评估分页或紧凑列表。

| 风险 | 应对 |
