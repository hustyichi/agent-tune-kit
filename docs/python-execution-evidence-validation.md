## 实现结果

- runner 在声明采集时持续写入每个 attempt 的 `events.jsonl`，保持 stdout 结果通道，保留开始、结束、异常和超时信息。旧配置继续使用原有行为。
- 随包提供标准 logging 的 JSON Handler；Loguru 项目复用原生 JSON stderr。每次执行带明确的 Case/执行身份，阶段与原生运行编号来自实际日志。
- 原生审计、阶段结果及工作簿直接进入现有批次证据索引，带内容指纹和所属执行；改动、缺失或路径越界不能被当作原证据读取。
- `view_execution` 与 `read_native_evidence` 提供固定分页读取，不执行 Agent、不调用模型、不创建 EvidenceBatch。知识来源组可沿原生引用回到所属 Execution。
- 未确认结果的中断 attempt 仍保留可查询轨迹，并标记执行未知；runner 故障、输出解码失败和裁剪有显式状态。大文件指纹校验使用分块读取。
- 接入、评测、诊断与共享 Skill 流程规定复用原生来源、按版本维护评分资产、清理临时操作文件，并限制摘要和探针的默认生成。

本次使用本地源码验证；包和插件版本号仍为 `1.1.0`，没有发布新版本或替换已安装发行版。新内部操作以该源码为准，应从 ATK 仓库执行 `uv run --frozen atk internal ...`。

### 异常定位实例

新方式中一个 Case 的匹配子项出现 `LLM_TIMEOUT`。先使用 `view_execution` 读取该执行，再使用 `read_native_evidence` 读取原生结果，共两次只读查询即可对上：

1. `model.request.retry`：LLM 第一次调用超时，准备第二次尝试。
2. `model.request.failed`：LLM 第二次调用仍超时，记录 `ModelConnectorError`。
3. 原生结果对应子项为 `RETRYABLE_FAILED`，错误码 `LLM_TIMEOUT`；同 Case 另一子项已完成。

这项检查新增模型调用 0、探针 0、审计导入批次 0。它定位到直接失败点，但没有证明远端超时来自网络、服务排队还是其他原因。

两侧拆分和入路均为 10/10；匹配和编码均为 8/10。呈现通过数从 5/10 变为 6/10，完整通过 Case 从 1/5 变为 2/5。模型具有随机性、远端版本未知且每侧仅一次重复，这些分数变化不归因为采集改造，也不宣称临床准确率提升。执行耗时合计分别约 546.6 秒与 535.1 秒，不能从单次模型调用样本推断日志改造带来性能改善。

## 适用范围与剩余限制

本次证明了本地 Python 独立进程、线程/asyncio 和原生 Loguru 审计接入的工程机制，未验证通用远程日志平台、共享服务中的多请求隔离或任意内部多进程汇集。此类项目需显式适配并检查覆盖。

手术项目的声明范围包含阶段开始、流水线最终状态、连接器事件和原生结果/审计。并未为每个内部分支记录结束事件，也没有让每条日志一一对应所有模型调用 span；细节仍需通过原生审计 ID 和业务子项关联查看。采集完整不等于全业务过程都可观察。

已覆盖采集文件丢失等失败路径；未通过破坏真实磁盘制造硬件故障或断电场景。正常退出与受控中断可保留已收到的记录，未输出或未刷盘的末尾内容无法恢复。

既有候选采用、真实调优收益和外部组件修复仍沿用原验收边界。本次不采用业务修复、不修改评分标准、不初始化或更新父仓 gitlink，也不发布新版。
