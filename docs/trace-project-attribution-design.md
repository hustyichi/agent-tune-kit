## 1. 结论与已确认决策

会话包含问题，具体问题关联项目。会话和问题分类均不保存独立项目归属，也不保存问题项目的并集。`source.project` 是轨迹来源命名空间，保持原义。项目多选使用可展开的复选菜单，提供清空、已选数量与键盘操作。

在现有 Trace 流程内增加工程目录、Issue 的多工程归因，以及大盘和会话页的根因项目展示与筛选。初始化建立可复用的工程边界，诊断按证据决定归因；项目发现本身不产生归因。页面首先回答“问题出在哪个项目”，修复详情再说明“在哪里修改、为什么这样改”。

## 3. 初始化：轻量探索与工程目录

建议新增 `.atk/traces/projects.json` 作为工程身份、位置和职责索引的唯一结构化来源，沿用私有归档的忽略规则。`project.md` 保留整体背景、执行与验证入口，只引用工程目录，避免再维护一份相同的工程表。

### 探索步骤

1. 确认归档工作区根，优先读取项目已有 README、`CLAUDE.md`、`AGENTS.md`、存在的 `rules.md` 及其明确指定的关系入口。按实际文件名读取，也支持项目使用的 `Claude.md`、`Agents.md` 等大小写形式；文件缺失记为信息缺口，不要求项目为 ATK 新建这些文件。
2. 根据 `.gitmodules`、Git index 中的 gitlink 和实际 checkout 识别子模块；已检出的子模块按相同方式识别嵌套层级。不能仅凭 `.git` 是否为目录判断仓库。
3. 普通工程目录从已确认的 workspace/package 配置、项目文档及用户指定路径登记，不把每个目录都当作独立工程。
4. 对候选工程及已检出的子模块，同样读取其自身 README、CLAUDE.md、AGENTS.md 等入口，提取名称／既有简称、职责、上下游关系、相关代码／Prompt／Skill／工具入口、修改约束与验证命令。父仓说明不能替代子仓规则；记录规则来源及适用目录，具体实现留到诊断时按线索读取，并记录尚未阅读的范围。工程目录保存摘要和引用，执行时仍回源适用的原文件，不复制一套规则或用摘要覆盖原规则。
5. 未检出的 submodule 保留已声明的身份、位置与父工程，标记“本地不可核验”；不自动 clone、初始化、checkout 或对齐 gitlink。

工程目录至少包含稳定 `id`、项目通用名称、相对工作区根的 `path`、`parent_id`、`kind`（repository/submodule/directory）、职责摘要与入口路径。可选记录已有简称／别名及其来源；MCS、APE、OT 只有在项目资料或用户已明确使用时才登记，不能由 ATK 按首字母自行生成。记录结构来源和核对时间，以及是否可读取；根工程的路径为 `.`。

ID 创建后稳定，名称和路径可以经明确更新调整。重名不能靠显示名自动合并；同名子目录需使用不同 ID。路径与父级关系必须校验，不允许越界、循环父级或把符号链接指向的工作区外目录自动纳入。

`projects.json` 带 `schema_version` 与 `revision`。更新沿用现有锁、原子写和 revision 冲突检查；重跑初始化只合并确认的变化，保留人工别名和职责说明。不再使用的工程标记停用，保留旧引用。

### 名称统一规则

- 项目名称和简称优先来自已有 README、CLAUDE.md、AGENTS.md、项目配置或用户明确说明，并保留来源。没有既有简称时使用项目通用名称；资料没有给出其他名称时沿用仓库／工程名称，不另起名字。
- 面向用户的默认显示名统一采用“已有简称，否则通用名称”。详情同时给出通用名称与路径；无简称时即使名称较长也不创造缩写，页面可换行或截断并提供完整名称。
- 初始化摘要、诊断、修复、验证、大盘标签和会话页使用同一个工程 ID 与命名规则；正文首次出现既有简称时可附完整名称。历史快照继续显示当时名称。
- 搜索和用户指定工程可匹配已有名称、简称、别名或路径。重名用完整名称和路径区分，不通过发明新简称消除歧义；稳定 ID 仅用于关联，不冒充展示简称。

### 工程目录管理

建议只增加一个轻量管理命令，与既有 `trace category` 保持相似：

```text
# 工程目录管理命令。
atk trace project --discover --project-root <workspace> --json
atk trace project --list --project-root <workspace> --json
atk trace project --data <entry.json> --project-root <workspace> --json
```

`--discover` 只返回本地结构候选，不生成语义结论；宿主补齐职责后用 `--data` 新增／修订一项，已有目录更新须携带当前 revision。复用 `atk-trace-init` 编排，不新增 Skill。最小 `atk trace init` 仍然可用，不要求完整探索才能导入或分析会话。

已有归档无需重做初始化：诊断发现工程目录缺失或相关入口已变化时，按本次调查范围补齐。用户直接指定一个未登记的本地工程路径时，也走相同登记与校验。

## 4. 诊断：根因归属与修改位置

### 用户需要理解的信息

| 信息 | 表达的事实 | 呈现位置 |
| --- | --- | --- |
| 根因项目 | 根因实现／规则属于哪个工程；未证实的判断标为待确认 | 问题视图、问题列表及诊断详情 |
| 修改位置与范围 | 计划或实际在哪个工程、哪些文件／行为上修复；与根因项目不同时说明原因 | 修复方案、实际改动与验证详情 |

一条问题可以有多个根因项目，不强制选一个“主责任项目”。通常在根因项目内修改，不需要额外展示一组相同的“改进项目”标签。若权衡后选择其他项目修改，修复详情用一句话说明目标和理由；不能因为修复落在其他项目就改变根因归属。根因未知但已有可行防护方案时，可以记录该方案，根因仍保持未确定。

某工程只是执行现场、分发包或调用方，不因此自动成为根因项目；例如 OT 中携带 APE 二进制，不改变 APE 源码的责任位置。通常修改位置与根因一致只是展示上的简化依据，不能用于自动推断根因、补写实际改动或声明修复有效。

每项关联仍可独立记录 `evidence_state`：`hypothesis`（待核实）或 `supported`（证据支持）。它衡量关联依据，不替代原有验证 outcome。根因的 supported 需要能解释本次问题的因果证据；修改方案有依据也不能展示为“修复有效”。缺少历史运行版本或加载证据时，不能仅凭当前源码把根因升为已确认。页面用“APE（待确认）”等直接文字表达不确定性，不暴露内部枚举或新增证据状态筛选。

### 数据落点

给 `issue.json` 增加可选 `project_links` 数组。内部可保留 `role` 区分根因与改进关联，复用此前的数据设计；它不是用户需要理解或选择的概念。页面统一从根因关联生成项目标签和筛选数据，修改位置由修复方案与实际改动表达。每项建议包含：

| 字段 | 含义 |
| --- | --- |
| `project_id` | 工程目录中的稳定 ID |
| `role` | 内部关联类型：`root_cause` 或 `improvement`；不作为页面字段、标签、筛选或用户指令参数 |
| `evidence_state` | `hypothesis` 或 `supported` |
| `reason` | 该工程与这条问题之间的具体关系，非空 |
| `evidence` | 复用既有归档引用格式，指向支撑关联的轨迹或调查记录 |
| `source_paths` | 可选，工作区相对的源码／Skill 路径及行号；仅作当前源码导航 |

同一 `(project_id, role)` 不重复；同一工程有两种关联时可分别记录依据和证据状态，页面不因此重复显示工程标签。关联必须有可追溯依据，必要时先保存调查记录，再引用它；源码导航链接本身不冒充历史运行证据。

通过现有 `atk trace issue` 写入，沿用当前 revision 与 history。更新省略 `project_links` 时保留原值，显式 `[]` 才清空；新关联校验工程 ID、角色、状态、路径和证据。停用工程的原有引用仍可读取，缺失目录或损坏项不能让整个会话消失。

诊断保存时把关联和用到的工程目录项快照一起冻结，包含目录 revision、当时名称／路径和实际检查的源码版本依据。诊断正文仍按“问题描述、问题根因、最小修复方案”组织：根因段明确所属工程，修复方案明确拟修改项目和范围；二者不同时说明选择该修改位置的原因。候选方案之间是替代还是互补，在正文说明，不引入另一套计划对象或面向用户的关联类型表。

快照保留当时信息，当前工程表的改名或移动不重写旧诊断。保存诊断需绑定已审阅的 Issue revision（建议为现有保存命令增加可选 revision 参数），避免项目关联并发修改后把旧正文和新关联错误配对。初始化时的 checkout 记录不能替代诊断时重新核对的 commit、dirty 状态和必要文件／diff 摘要，也不能冒充线上加载版本。

### 指定项目的使用方式

```text
$atk-trace-init 梳理当前工作区及子模块，重点登记 MCS、APE、OT 的职责与入口。

$atk-trace-diagnose 调查 <session-id>，优先检查 APE 和 OT，
定位根因所属项目，并说明拟修改的位置和范围；证据指向其他项目时继续调查。
```

以上行为由更新后的 Skill 编排。名字、别名或工作区内路径先解析成已登记 ID，重名且无法判定时才澄清。调查意图记录在本次覆盖说明和诊断中，不作为问题归因字段。CLI 负责结构校验与保存，语义归因仍由宿主执行。

### 诊断中的项目与范围

每项根因说明同时写明项目、模块／代码／规则位置和证据；每条最小修复建议同时写明目标项目、拟修改的目录／文件或具体行为，以及对应验收条件。跨项目方案逐项目列出，说明各自解决哪一部分、是否需要共同实施。不能只写“修改 APE／OT”而没有对应范围，也不能把调查过的工程全部当作计划修改工程。

诊断覆盖说明按项目区分已检查范围、未检查范围和证据缺口。尚无法确定修改位置时明确标为待定位并给出下一步检查，不编造文件名。扩大调查范围仍按用户已确认的“指定工程优先、证据可指向其他工程”处理。

检测阶段可以保留有证据的待核实关联，不要求先给根因结论。诊断负责确认、修订或撤销关联；被否定的旧假设保存在历史和正文中，不继续作为当前根因展示。无关联不等于已排除，不因指定工程内未找到根因而停止检查。

## 5. 大盘与会话页

### 大盘

继续提供“会话／问题分类”两个视图，只增加“根因项目”多选。问题分类汇总和问题行的项目标签都来自具体问题的根因归属；不出现“角色”“改进项目”控件，不新增按修改项目筛选或统计的入口。新增的工程名称／别名搜索索引也只取根因关联，通用标题等文本搜索沿用现有行为。沿用现有组件、样式与离线页面，不新增 UI 依赖。

```text
根因项目：[APE ×] [OT ×]   来源：[全部 ▾]
当前筛选：3 个会话 · 4 个问题

ISSUE-001  ……问题标题……

```

- 问题抽屉中的每条问题只显示根因项目标签；项目较多时展示前几个和 `+N`，展开可看全。已获支持的根因直接显示项目名，候选根因附“待确认”，不额外排列内部类型与证据状态标签。
- 分类卡片显示“该类问题涉及的根因项目”及去重问题数；会话卡片仅显示会话事实、问题数量与进度，不展示项目归属。拟修改或实际修改的其他项目不混入这些标签与统计。
- 多选根因项目使用 OR，与来源、搜索和进度使用 AND。候选根因也可被其项目筛选命中，但始终标明待确认。仅有“APE 根因、OT 修改”的问题只能被 APE 项目筛选命中；选 OT 不能因为修改位置在 OT 就命中。
- 项目筛选精确匹配问题实际关联的项目 ID。工程目录支持包含子项目的复杂工作区，父子结构不参与筛选匹配：问题归因到子项目时，仅选择该子项目才能命中；选择父项目只命中直接关联父项目的问题，不自动包含子项目，也不向 Issue 补写父级归因。
- 保留“待归因”入口，涵盖尚未记录根因项目的问题，包括已有修复建议但根因仍未知的问题。已证实原因在登记工程以外时，在详情明确说明，不能以修改项目补齐归属。没有问题的会话在未筛选视图继续可见，不推断其根因工程。
- 当前筛选的问题数、会话数和列表保持一致。进度图例按当前根因项目／来源／搜索范围计算各进度数量，点击图例再过滤列表，避免选中一档后其他档消失。
- 计数以当前归档内的会话身份加 Issue ID 去重。一条问题命中多个根因项目也只计一次；各工程分项之和可以大于总问题数，不能直接相加为总计。内部存在改进关联不影响项目统计。
- 根因项目选择与现有抽屉定位写入 URL hash，例如 `#view=category&project=asset-protocol-engine`；多个根因项目用重复参数。问题视图保留项目筛选，切回会话总览不受项目条件影响；旧的会话项目筛选链接转入问题视图，明确指定会话的链接保留会话定位，不引入角色参数。

### 会话页

- 会话概览只显示会话事实；根因项目标签与筛选仅位于内部问题列表，不影响原始轨迹与证据。
- 左侧问题卡片与问题详情摘要使用同一套根因项目标签，详情可查看归因依据和源码入口，不并列展示一份“改进项目”清单。
- 修复方案及实际改动沿用已有阶段摘要，按项目说明拟修改／实际修改的位置和范围。修改就在根因项目内时正常展示文件与改动，不重复强调两种项目身份；修改在其他项目时写清“在 OT 的某个 Skill 修改，因为……”，同时说明该方案的作用与限制。提议与已执行改动保持区分。
- 诊断记录展示自己的历史项目快照，明确区别于 Issue 当前关联，不把旧诊断显示成最新判断。
- 问题栏只支持与大盘一致的根因项目筛选；从大盘打开指定问题时保留根因项目上下文与既有 Issue 深链。筛选只控制问题列表，不删减原始泳道和事件证据；明确选中的问题不能被冲突筛选悄悄隐藏。
- 根因项目标签可跳回大盘的对应筛选；修复详情中的项目名称仅用于说明修改位置。两个页面从同一份工程目录与 Issue 归因读取，不在 HTML 中从修改路径反向推断根因。

工程目录更新也会影响页面有效性，须纳入过期检测。阶段结束沿用既有“刷新当前会话页一次，再刷新大盘一次”的机制；其他受影响的旧会话预览标记待刷新，不为展示更新重写历史记录。若目录缺失或损坏，仍显示关联 ID 和缺口提示；不能静默吞掉问题。

## 6. 与修复、验证及历史记录的衔接

`atk-trace-optimize` 读取已采用诊断中的工程关联和实际方案，进入目标子仓前读取该仓规则、核对状态。APE 与 OT 可以是替代方案，也可以共同完成一个方案；存在两个改进关联不等于授权同时修改两个仓库。实际授权与选定方案决定修改范围。

通常在根因所属项目修复，按真实方案记录即可。选择其他项目作为更合适的修改位置时，诊断方案和改动摘要说明原因及取舍，例如是否属于调用前防护、规避或根本修正，以及仍有哪些限制；不把修改项目自动加入根因列表。大盘的归属和筛选不会因修复位置变化而变化，只有新的归因证据才可改变它。

各阶段统一以工程目录的 `project_id` 关联，按以下口径表达范围：

| 阶段 | 每个项目必须明确的信息 |
| --- | --- |
| 诊断 | 已查模块／路径、根因或假设、拟修改位置与行为、依据及验收条件；未检查范围另列 |
| 修复开始 | 采用哪条诊断方案、目标项目、计划修改范围、实际基线及适用的项目规则 |
| 修复完成 | 实际修改的项目和文件／行为、candidate／diff、本地检查；与原方案存在差异时说明原因，未实施的项目方案仍标为未实施 |
| 验证 | 对应项目和候选版本、实际加载证据、执行检查的范围与结果；多项目联动时补充整条链路的验证结论 |

修复记录继续使用现有 `before`、`candidate`、`diff`、`checks` 和摘要机制，按实际改动工程分别记录版本／diff／检查。修复与验证的逐项摘要绑定同一 `project_id`，文件路径统一相对归档工作区根，校验其归属；涉及多个工程时逐工程列出，避免一个项目标签覆盖所有改动。兼容旧记录中没有工程 ID 的摘要，显示“项目未记录”，不自动推断后改写历史。

修改前核对计划范围，完成后用真实 diff 核对实际范围。执行中需要增加项目或扩大修改范围时，先说明原因、更新范围，并依据现有授权判断是否继续；只有超出已授权边界才另行确认。调查中发现一个项目，或关联为改进项目，本身不授予写入权限。

验证逐个核对真正加载的工程候选；不能只记录 Magic 父仓 commit，不能只凭本地单测把整条问题判为修复有效。父仓 gitlink 不因诊断、修复记录或收尾而自动更新。

兼容规则：

- 老归档没有 `projects.json` 或根因项目记录仍能打开，显示“待归因”；只有改进关联的记录也不冒充已经归因，无须重新下载或搬移会话。
- 若旧版已有名为 `projects.json` 的会话目录，保留其读取能力并报告目录冲突；新保留名规则不能让旧会话失效，也不能自动移动它或用配置文件覆盖它。迁移需按既有归档迁移边界单独处理。
- 重新诊断指定 Issue 时补齐有依据的关联，不要求先重跑全会话检测。已有诊断可复用有效证据，但补充结论须保存新的诊断快照，不改旧文件及其摘要哈希。
- 若需要批量补关联，可从既有诊断提取候选并逐项核对；不能只靠正文出现项目名就认定根因，也不默认改写所有历史会话。
- 可视化只读生成，不补写关联或偷偷迁移数据。实际归因仍经记录写入流程。
- `source.project`、Session ID、已有问题分类、实际进度和批量评测契约保持原义。

## 7. 实施范围与验收

按下列顺序完成同一条链路；只有数据、诊断与两个页面都打通，才算本需求交付。

| 顺序 | 改动面 | 复用与必要联动 |
| --- | --- | --- |
| 1. 工程目录和关联记录 | 新增 `traces/projects.py`；修改 `cli/trace.py`、`traces/records.py`、`traces/archive.py` | 复用现有路径／锁／原子写／revision 工具；增加 `projects.json` 保留文件名，防止 Session ID 与其冲突；诊断快照及并发核对、修复／验证摘要的项目引用同步覆盖新字段 |
| 2. Skill 流程与契约 | init、detect、diagnose、optimize、verify、visualize-trace；`docs/trace-tuning.md` 及中英文 README | 初始化阅读既有规则与名称、按项目优先诊断、按项目明确调查／修改范围、记录更新、跨仓候选与加载证据、页面刷新；capture 的来源身份与采集逻辑无须扩张 |
| 3. 展示与回归 | `visualize/trace.py`、`visualize/traces.py`、两套页面 assets 和相关 tests | 共享根因项目读取／校验及命名结果；问题根因标签、筛选、去重、深链、历史快照、修复详情中的修改范围与取舍、过期提示与可访问性一起验收，不增加角色或修改项目筛选 |

关键验收场景：

1. 普通单仓、显式普通目录、多 submodule 和嵌套 submodule 均可登记；缺失 checkout 仍可展示边界。重跑保留人工字段，路径／别名歧义可见，父级循环及越界路径拒绝。
2. 同一 Issue 根因在 APE、可在 APE 或 OT 修改：大盘问题视图和会话内问题列表只显示 APE 根因标签，APE 项目筛选命中、OT 项目筛选不命中。只有 OT 也有独立的归因依据时才增加其根因标签，待确认者必须明确标注；命中多个根因或父级时不重复计数。只有修改建议而无根因归属时仍显示待归因。
3. 指定 APE／OT 后，若证据指向其他登记工程，调查继续并保存依据；仅出现工程名、调用传播或当前源码缺陷不足以确认历史根因。
4. 修订关联保留 history；省略保留、空数组清空；已保存诊断和采用的哈希不变；并发 revision 冲突不能错配正文与关联。
5. 未关联、停用／改名／移动工程、目录损坏、零问题会话及旧归档仍可浏览。新保留文件名不会与新会话目录冲突，旧同名会话仍可读取并报告迁移缺口；源码链接维持边界检查。
6. 大盘两个视图、抽屉、统计、单会话页、根因项目标签及深链一致；页面无角色选择器、内部类型标签或修改项目筛选。桌面和窄屏均可操作，筛选不影响原始证据访问。目录修订后的预览会正确提示过期。
7. APE／OT 多仓方案分别记录候选与实际加载证据；验证失败或未知不会改变项目关系为“已修复”。选用一条替代方案时，不把另一工程虚报为已修改。
8. 初始化读取根工程及相关子模块实际存在的 README、CLAUDE.md、AGENTS.md（含实际大小写变体），保留规则来源与适用范围；没有这些文件仍可登记项目。已有简称从来源沿用，无简称时各阶段和页面均使用通用名称，不生成新简称。
9. 同一方案在诊断、修复开始、修复完成和验证中能按项目对应到拟修改范围、实际 diff 与检查结果；修改位置与根因项目不同时说明选择原因及限制，根因归属不随修改位置自动变化。相同项目不重复展示两份项目标签，部分项目未实施、范围变化及加载缺口清晰可见。旧修复／验证摘要没有项目 ID 时仍能读取。

实现时扩展 `tests/test_trace_store.py`、`test_trace_records.py`、`test_trace_cli.py`、`test_visualize_trace.py`、`test_visualize_traces.py` 和现有 Node 页面测试，并为工程目录加聚焦测试。Skill／模板改变后按仓库规范运行完整 pytest 和 skill-pack 校验；使用 `uv run --frozen` 避免无关 lockfile 改动。再核对 Ruff、JS 语法、包内资源和浏览器交互。真实 Magic 样本使用隔离副本验证展示与只读性，语义归因另选具体问题核验，不能用数据结构测试替代。

最初方案阶段只进行了本地结构核对。后续实现范围见下方记录；未改写 Magic 私有归档或运行真实效果回放。
