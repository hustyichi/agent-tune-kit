# Trace 多工程关联与筛选

日期：2026-11-11（Asia/Shanghai）。本文件记录当前实现契约。来源：用户在 Magic Workspace 调优中对归因口径的澄清，以及统一为“关联项目”、不兼容旧关联结构的明确要求。

## 归因口径

归因表示本次诊断认为问题可能由哪个项目的什么原因导致。有基于实际材料、相对合理的逻辑解释即可建立关联，供人审核；不以完整证明、完成修复或验证修复有效为前提。

解释可以涉及代码行为、配置、工具契约、Prompt、Skill 的具体规则或缺口，以及项目之间的相互作用。缺少历史部署版本、尚未回放、有竞争解释，应在关联理由与诊断正文中说明，不自动阻止关联。修复未通过只说明该次修复的效果；新证据是否推翻原因解释，需要另行判断。

一个项目被提到、是调用现场或适合放置防护，并不自动产生关联。需要解释该项目的具体机制如何导致或放大这条问题。没有合理项目解释时保留空关联，并在诊断中说明原因。无关联项目可以表示没有适用项目，不自动意味着归因尚未完成；确实存在信息缺口时才说明缺口。

## 数据与保存

项目目录继续使用 `.atk/traces/projects.json`。稳定 ID、已有名称／简称、相对工作区路径、父子关系、职责和入口保持现有契约：

- `atk trace project --discover --project-root <workspace> --json` 只读发现工程及子模块。
- `atk trace project --list --project-root <workspace> --json` 读取目录。
- `atk trace project --data <entry.json> --project-root <workspace> --json` 保存项目，更新必须携带目录当前 revision。
- 不凭名称合并项目、不自行编造简称；默认显示已有简称，否则项目名称。
- 读取各项目自身的 README、AGENTS.md、CLAUDE.md 等入口。未检出的子模块只记录本地不可核验，不自动初始化或对齐 gitlink。

只有 Issue 拥有项目关联。会话、分类均不保存项目并集；`source.project` 继续表示轨迹来源命名空间，`--project-root` 继续指向归档工作区。

Issue 的 `project_links` 是列表，每个项目最多一项，允许关联多个项目：

| 字段 | 契约 |
| --- | --- |
| `project_id` | 已登记项目的稳定 ID |
| `reason` | 非空文本；说明具体项目机制与本问题的关系，并写明不确定性 |
| `evidence` | 非空的归档证据引用列表；保持路径、哈希及可选 JSON Pointer 校验 |
| `source_paths` | 可选的工作区相对源码路径列表；保持路径边界校验 |

例如，一个尚未回放的解释也能保存：

```json
{
  "project_id": "toolkit",
  "reason": "实际加载的审阅规则未说明样式预算耗尽后的补采步骤，可能促成了覆盖范围误报；工具已给出补采提示，规则缺失的独立影响仍待回放。",
  "evidence": [{"path": "raw/trace.json", "sha256": "<retained-file-sha256>", "pointer": "/observations/0"}],
  "source_paths": ["toolkit/skills/review/SKILL.md"]
}
```

不再接收 `role`、`evidence_state`，不维护根因／改进项目两套关系，也不增加置信度分数或审批状态。新写入拒绝未知关联字段、未知项目、重复项目、空理由、空证据及越界路径。不提供旧关联结构的转换命令或兼容分支。

通过 `atk trace issue` 保存关联；更新携带 Issue 当前 revision。省略 `project_links` 保留原值，`[]` 清空，新 Issue 默认为 `[]`。标题等其他更新不应无意丢失关联。

诊断保存时校验关联并冻结 Issue revision、关联列表和当时的项目目录。旧诊断不被覆盖，后续关联变更不改变已采用诊断的依据。

## 诊断与修复流程

`atk-trace-diagnose` 的每条问题必须完成：

1. 从原始证据、已有诊断和相关实现形成合理的原因解释；观察事实与推断分开，写出限制。
2. 将正文提到的项目解释与 `project_links` 对齐，通过 `atk trace issue` 保存。即使问题范围未变，也要核对关联；复用旧诊断不能跳过此步。没有合理解释则保存空列表，并在正文说明原因。
3. 使用更新后返回的 revision 执行 `atk trace diagnose --expected-revision ...`，让快照和审阅内容一致。关联变化时保存新诊断，不改写旧文件。
4. 所有写入完成后，统一刷新会话 preview 和工作区 dashboard。

init、detect、optimize、verify、visualize 的项目说明使用同一套关联语义。检测可以保留具体实现线索；诊断不要求先证明修复效果；修复选取已有解释开展工作；验证单独判断实际候选是否加载、执行是否完成以及每条问题的效果。

修改项目、文件和行为由原有修复方案、实际 diff、`change_summary` 和验证记录表达。跨项目修复需要说明选择该位置的理由，但不自动改变关联。一个项目进入关联列表也不授予修改权限；跨仓操作继续遵守既有边界。

## 页面行为

两种页面均从同一项目目录和 Issue 关联生成 `linked_projects`，展示与筛选覆盖全部关联项目，不依赖证明强度或修复状态。

- 大盘的问题视图、会话页的问题列表显示“关联项目”；空列表显示“关联项目：无”，说明使用“无关联项目”，项目筛选只列出实际项目，不提供空关联选项；历史空关联筛选参数按未筛选处理。分类卡片只汇总当前筛选命中问题的真实项目并去重，全部为空才显示“关联项目：无”；抽屉逐条展示实际关联。会话总览不按项目过滤，也不展示会话级项目并集。
- 项目多选采用 OR，与来源、搜索和进度采用 AND；项目身份精确匹配，不把父项目自动扩展为全部子项目。
- 同一问题命中多个项目只计一次；各项目分项不能直接相加作为问题总数。
- 关联项目的名称和别名进入问题搜索；修改记录中的项目名称不反向生成关联。
- 筛选保留 URL hash、Issue 深链和项目标签跳转。显式打开的问题保持可见；项目筛选不删减原始泳道和事件证据。
- 诊断详情展示保存时的项目名称及关联理由，包括最新的结构化诊断；人工可直接审阅解释。不再附“待确认”的证据强度标签。

## 原问题定位

2026-11-11 核对 Magic Workspace 的既有产物：5 个会话目录、其中 4 个包含 25 条问题，均有诊断。原结构中只有 1 条问题带根因关联，10 条只有改进关联，另 14 条没有 `project_links`；全部 12 项已保存关联都标记为 supported。

问题由两层共同造成：

1. Skill 把缺少历史加载证明、尚未证明改动有效等限制混入项目归因，促使有解释的项目只写为改进位置；正文与结构化关联也缺少逐条核对。
2. 数据模型要求根因／改进角色及证据状态，页面只读取根因角色。已有改进关联因此被显示为空关联。未保存的关联则无法由页面补出。

本次修正删除角色分流、把不确定性留在理由中，并把保存关联及冻结最新 revision 纳入诊断主流程。页面不从正文自动猜测项目，避免把提及或修复建议变成未经解释的关联。

验证覆盖新结构保存、边界校验、诊断快照、两个页面的一致性、多项目筛选与去重。真实 traces 只用于本地验证，不进入公开测试夹具；修复有效性和新宿主是否加载 Skill 需要各自的实际证据。
