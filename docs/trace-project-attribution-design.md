# Trace 多工程关联与筛选方案

日期：2026-11-10（Asia/Shanghai）。状态：**建议方案，尚未实现**。本次用户已确认关联角色及指定项目的调查语义；其余数据与交互设计为建议，不能作为现有功能说明。

## 1. 结论与已确认决策

在现有 Trace 流程内增加工程目录、Issue 的多工程关联，以及大盘和会话页的展示与筛选。初始化建立可复用的工程边界，诊断按证据决定关联；项目发现本身不产生归因。

| 决策 | 约定 | 来源 |
| --- | --- | --- |
| 关联角色 | 区分“根因项目”和“修正／改进项目”；每种角色均可关联多个工程，一个工程也可兼具两种角色 | 用户本次确认 |
| 指定工程 | 优先调查指定工程，证据指向其他工程时继续调查和关联；指定工程不预设根因 | 用户本次确认 |
| 支持对象 | 普通工程、Git 仓库、submodule 和嵌套 submodule；支持显式指定工程 | 用户本次需求 |
| 展示 | 大盘异常信息显示关联项目，支持项目筛选；会话页显示对应关联信息 | 用户本次需求 |

建议保持一个调优工作区、一份 `.atk/traces/`。例如 Magic 根目录保存会话，MCS、APE、OT 是其中可关联的工程，不要求每个子仓单独初始化、复制会话或建立大盘。

第一版覆盖归档工作区内的工程及嵌套子模块。跨工作区聚合、工作区外独立 checkout 的绑定、页面内编辑和工程关系图不纳入本次范围；当前 Magic 示例不需要这些能力。

## 3. 初始化：轻量探索与工程目录

建议新增 `.atk/traces/projects.json` 作为工程身份、位置和职责索引的唯一结构化来源，沿用私有归档的忽略规则。`project.md` 保留整体背景、执行与验证入口，只引用工程目录，避免再维护一份相同的工程表。

### 探索步骤

1. 确认归档工作区根，读取该项目的 README、适用规则和明确指定的关系入口。
2. 根据 `.gitmodules`、Git index 中的 gitlink 和实际 checkout 识别子模块；已检出的子模块按相同方式识别嵌套层级。不能仅凭 `.git` 是否为目录判断仓库。
3. 普通工程目录从已确认的 workspace/package 配置、项目文档及用户指定路径登记，不把每个目录都当作独立工程。
4. 对候选工程先读入口与规则，记录职责摘要和相关代码／Prompt／Skill／工具入口；具体实现留到诊断时按线索读取。记录尚未阅读的范围。
5. 未检出的 submodule 保留已声明的身份、位置与父工程，标记“本地不可核验”；不自动 clone、初始化、checkout 或对齐 gitlink。

工程目录至少包含稳定 `id`、显示名、相对工作区根的 `path`、`parent_id`、`kind`（repository/submodule/directory）、职责摘要与入口路径。可选别名支持 MCS、APE、OT。记录结构来源和核对时间，以及是否可读取；根工程的路径为 `.`。

ID 创建后稳定，名称和路径可以经明确更新调整。重名不能靠显示名自动合并；同名子目录需使用不同 ID。路径与父级关系必须校验，不允许越界、循环父级或把符号链接指向的工作区外目录自动纳入。

`projects.json` 带 `schema_version` 与 `revision`。更新沿用现有锁、原子写和 revision 冲突检查；重跑初始化只合并确认的变化，保留人工别名和职责说明。不再使用的工程标记停用，保留旧引用。

建议只增加一个轻量管理命令，与既有 `trace category` 保持相似：

```text
# 以下为拟议命令，当前版本尚不支持。
atk trace project --discover --project-root <workspace> --json
atk trace project --list --project-root <workspace> --json
atk trace project --data <entry.json> --project-root <workspace> --json
```

`--discover` 只返回本地结构候选，不生成语义结论；宿主补齐职责后用 `--data` 新增／修订一项，已有目录更新须携带当前 revision。复用 `atk-trace-init` 编排，不新增 Skill。最小 `atk trace init` 仍然可用，不要求完整探索才能导入或分析会话。

已有归档无需重做初始化：诊断发现工程目录缺失或相关入口已变化时，按本次调查范围补齐。用户直接指定一个未登记的本地工程路径时，也走相同登记与校验。

## 4. 诊断：一条异常，多种项目关系

### 两种角色

| 角色 | 表达的事实 | 不能由此推出 |
| --- | --- | --- |
| `root_cause`，根因项目 | 根因实现／规则属于该工程，或这是有明确依据的待验证归因 | 在该项目观察到错误就意味着它是根因 |
| `improvement`，修正／改进项目 | 有针对该异常的具体修正、约束或防护方案可在该工程实施 | 该工程有缺陷、方案已采用，或修复效果已通过验证 |

两种角色都允许多个项目；不强制选一个“主责任项目”。根因未知时允许只有改进项目，或者暂时没有关联。某工程只是执行现场、分发包或调用方，不因此自动获得根因角色；例如 OT 中携带 APE 二进制，不改变 APE 源码的责任位置。

每项关联独立记录 `evidence_state`：`hypothesis`（待核实）或 `supported`（证据支持）。它衡量关联依据，不替代原有验证 outcome。根因的 supported 需要能解释本次异常的因果证据；改进的 supported 只表示改进位置和机制有依据，不能展示为“修复有效”。缺少历史运行版本或加载证据时，不能仅凭当前源码把根因升为已确认。

### 数据落点

给 `issue.json` 增加可选 `project_links` 数组，每项建议包含：

| 字段 | 含义 |
| --- | --- |
| `project_id` | 工程目录中的稳定 ID |
| `role` | `root_cause` 或 `improvement` |
| `evidence_state` | `hypothesis` 或 `supported` |
| `reason` | 该工程与这条异常之间的具体关系，非空 |
| `evidence` | 复用既有归档引用格式，指向支撑关联的轨迹或调查记录 |
| `source_paths` | 可选，工作区相对的源码／Skill 路径及行号；仅作当前源码导航 |

同一 `(project_id, role)` 不重复；同一工程有两个角色时分两项，允许两种角色有不同依据和证据状态。关联必须有可追溯依据，必要时先保存调查记录，再引用它；源码导航链接本身不冒充历史运行证据。

通过现有 `atk trace issue` 写入，沿用当前 revision 与 history。更新省略 `project_links` 时保留原值，显式 `[]` 才清空；新关联校验工程 ID、角色、状态、路径和证据。停用工程的原有引用仍可读取，缺失目录或损坏项不能让整个会话消失。

诊断保存时把关联和用到的工程目录项快照一起冻结，包含目录 revision、当时名称／路径和实际检查的源码版本依据。诊断正文仍按“异常描述、异常根因、最小修复方案”组织，分别写明根因工程与改进工程；候选方案之间是替代还是互补，在正文说明，不引入另一套计划对象。

快照保留当时信息，当前工程表的改名或移动不重写旧诊断。保存诊断需绑定已审阅的 Issue revision（建议为现有保存命令增加可选 revision 参数），避免项目关联并发修改后把旧正文和新关联错误配对。初始化时的 checkout 记录不能替代诊断时重新核对的 commit、dirty 状态和必要文件／diff 摘要，也不能冒充线上加载版本。

### 指定项目的使用方式

```text
$atk-trace-init 梳理当前工作区及子模块，重点登记 MCS、APE、OT 的职责与入口。

$atk-trace-diagnose 调查 <session-id>，优先检查 APE 和 OT，
分别记录根因项目与修正改进项目；证据指向其他项目时继续关联。
```

以上描述拟议行为。名字、别名或工作区内路径先解析成已登记 ID，重名且无法判定时才澄清。调查意图记录在本次覆盖说明和诊断中，不作为问题归因字段。CLI 负责结构校验与保存，语义归因仍由宿主执行。

检测阶段可以保留有证据的待核实关联，不要求先给根因结论。诊断负责确认、修订或撤销关联；被否定的旧假设保存在历史和正文中，不继续作为当前根因展示。无关联不等于已排除，不因指定工程内未找到根因而停止检查。

### Magic 示例

以下仅示意关系，不是在确认真实缺陷：

| 同一异常的调查结果 | 项目关联 |
| --- | --- |
| 证据表明 APE 的校验逻辑存在漏洞，修正它能阻止错误输入 | APE：根因项目；APE：修正／改进项目 |
| OT 的 Skill 可补充调用前检查、正确使用方式或结果说明 | OT：修正／改进项目；不因此标为根因 |
| 异常在 MCS 回合中出现，但尚未发现 MCS 自身的因果缺陷 | 不自动关联 MCS 为根因 |

如果后来发现 OT 的错误指令也是造成同一异常的原因，可以再增加 OT 的根因角色。如果发现的是没有已证实因果联系的独立缺陷，仍按既有规则另建关联 Issue，不把多个缺陷塞入一条异常。

## 5. 大盘与会话页

### 大盘

继续提供“会话／异常分类”两个视图，增加“关联项目”多选和“角色：全部／根因／修正改进”。搜索同时匹配工程名称与别名。沿用现有组件、样式与离线页面，不新增 UI 依赖。

```text
关联项目：[APE ×] [OT ×]   角色：[全部 ▾]   来源：[全部 ▾]
当前筛选：3 个会话 · 4 个问题

ISSUE-001  ……异常标题……
根因：APE（证据支持）   改进：APE、OT   进度：已诊断
```

- 异常抽屉中的每条问题都显示关联项目与角色；项目较多时展示前几个和 `+N`，展开可看全。
- 分类卡片显示命中问题的主要项目及去重问题数；会话卡片显示其问题关联项目的并集。详情再显示完整列表。
- 多选项目使用 OR，与来源、搜索、角色和进度使用 AND。工程与角色必须匹配同一条关联：仅有“APE 根因、OT 改进”的问题，不能被“APE＋改进”命中。
- 层级筛选默认包含所选工程及其子工程，并显示“含子项目”。父级用于筛选分组，不向 Issue 自动补写父级归因。
- 保留“未关联项目”入口。没有问题的会话在未筛选视图继续可见，不推断其根因工程。
- 当前筛选的问题数、会话数和列表保持一致。进度图例按当前工程／角色／来源／搜索范围计算各进度数量，点击图例再过滤列表，避免选中一档后其他档消失。
- 计数以当前归档内的会话身份加 Issue ID 去重。一条异常命中 APE、OT 或两个角色都只计一次；各工程分项之和可以大于总问题数，不能直接相加为总计。
- 项目选择、角色与现有抽屉定位写入 URL hash，例如 `#view=category&project=asset-protocol-engine&project_role=improvement`；多个项目用重复参数。切换视图保留筛选，旧深链继续可用。

### 会话页

- 顶部显示“问题关联项目”，从本会话 Issue 派生，避免新增一份可独立编辑的会话关联表。无关联时显示“尚未关联”。
- 左侧问题卡片显示简短项目标签；问题详情分列根因项目、修正／改进项目，提供依据、证据状态和源码入口。
- 诊断记录展示自己的历史项目快照，明确区别于 Issue 当前关联，不把旧诊断显示成最新判断。
- 问题栏支持项目／角色筛选；从大盘打开指定问题时保留项目上下文与既有 Issue 深链。筛选只控制问题列表，不删减原始泳道和事件证据；明确选中的问题不能被冲突筛选悄悄隐藏。
- 标签可跳回大盘的对应项目筛选。两个页面从同一份工程目录与 Issue 关联读取，不在 HTML 中反向推断项目。

工程目录更新也会影响页面有效性，须纳入过期检测。阶段结束沿用既有“刷新当前会话页一次，再刷新大盘一次”的机制；其他受影响的旧会话预览标记待刷新，不为展示更新重写历史记录。若目录缺失或损坏，仍显示关联 ID 和缺口提示；不能静默吞掉问题。

## 6. 与修复、验证及历史记录的衔接

`atk-trace-optimize` 读取已采用诊断中的工程关联和实际方案，进入目标子仓前读取该仓规则、核对状态。APE 与 OT 可以是替代方案，也可以共同完成一个方案；存在两个改进关联不等于授权同时修改两个仓库。实际授权与选定方案决定修改范围。

修复记录继续使用现有 `before`、`candidate`、`diff`、`checks` 和摘要机制，按实际改动工程分别记录版本／diff／检查。验证逐个核对真正加载的工程候选；不能只记录 Magic 父仓 commit，不能只凭本地单测把整条异常判为修复有效。父仓 gitlink 不因诊断、修复记录或收尾而自动更新。

兼容规则：

- 老归档没有 `projects.json` 或 `project_links` 仍能打开，显示“未关联项目”；无须重新下载或搬移会话。
- 若旧版已有名为 `projects.json` 的会话目录，保留其读取能力并报告目录冲突；新保留名规则不能让旧会话失效，也不能自动移动它或用配置文件覆盖它。迁移需按既有归档迁移边界单独处理。
- 重新诊断指定 Issue 时补齐有依据的关联，不要求先重跑全会话检测。已有诊断可复用有效证据，但补充结论须保存新的诊断快照，不改旧文件及其摘要哈希。
- 若需要批量补关联，可从既有诊断提取候选并逐项核对；不能只靠正文出现项目名就认定根因，也不默认改写所有历史会话。
- 可视化只读生成，不补写关联或偷偷迁移数据。实际归因仍经记录写入流程。
- `source.project`、Session ID、已有异常分类、实际进度和批量评测契约保持原义。

## 7. 实施范围与验收

按下列顺序完成同一条链路；只有数据、诊断与两个页面都打通，才算本需求交付。

| 顺序 | 改动面 | 复用与必要联动 |
| --- | --- | --- |
| 1. 工程目录和关联记录 | 新增 `traces/projects.py`；修改 `cli/trace.py`、`traces/records.py`、`traces/archive.py` | 复用现有路径／锁／原子写／revision 工具；增加 `projects.json` 保留文件名，防止 Session ID 与其冲突；诊断快照及并发核对同步覆盖新字段 |
