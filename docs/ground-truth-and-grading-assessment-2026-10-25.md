# Ground truth 与评分方案支持评估

前半部保留初查基线；模块化建议和资产设计保留提出时状态，当前实现与核验见文末「实现交付」。历史业务效果验收未刷新。

## 问题与结论

用户问题：ATK 作为执行调优项目，依赖数据集准备；其中 ground truth 与评分方案的确定较困难，目前如何支持，是否足够？

**结论：足以启动小规模、有人复核、业务标准相对明确的调优；尚不足以单靠 ATK 建立可信 ground truth 和经过校准、可重复的评分体系。**

当前支持较强的是保留数据、反馈修订、逐条判定、未知状态处理与结果追溯。支持较弱的是从模糊业务目标形成验收标准、证明答案有可信依据、证明裁判判得可靠，以及冻结跨轮比较的标准。这些工作目前主要交给用户和当前 Codex 会话。

这里要分别回答三个问题：

1. 什么算正确：每个样本的参考答案、允许的答案集合或验收条件。
2. 如何判断正确：规则、语义裁判、分级标准、硬失败条件。
3. 如何说明整体改善：汇总口径、未知比例、可比样本、回归保护范围。

ATK 对这三层都有入口，但只有部分环节有固定脚本保障。能填写 expected 字段、能生成判定文件，不等于前两层已被可靠确定。

## 目前如何准备 ground truth

实际流程是：业务资料或已有数据 → `atk-dataset` → 可选数据浏览与反馈 → `atk-dataset` 定向修订 → `atk-init` / `atk-eval`。

| 环节 | 当前支持 | 实际边界 |
|---|---|---|
| 输入与样本构建 | 接收已有 CSV、小文件、业务规则、代表性样例；优先常见成功、已知失败和边界样本 | 样本选择与补答案由 Codex 完成，没有固定的领域标注器 |
| 正确结果的表达 | 直接复用 `expected`、`label`、`acceptance_criteria`、`ground_truth`；精确答案与自然语言验收条件可以共存 | 能容纳不同表达，但没有固定流程帮助用户选择和完善判定方式 |
| 可信依据 | 禁止把被测 Agent 输出直接复制成可信答案；禁止编造领域事实；缺依据可留空 | 属于 Skill 指令，脚本不验证来源真实性或答案语义 |
| 标准共识 | 可选 `.atk/context.md` 记录必须包含、可省略、允许变化、拒绝条件、边界案例和已确认决策 | 是项目级已确认共识，不是逐样本证据或审阅记录 |
| 人工修订 | 支持对话反馈或 `dataset_review.csv`；按稳定 `atk_id` 结合输入理解反馈，允许只改选定答案字段 | 反馈文本还需 Codex 转译为有依据的修订，不是直接粘贴为答案 |
| 安全写入 | helper 校验 CSV、ID、更新范围，保留无关字段和顺序，原子替换，无变化保留原字节 | 保护数据完整性，不保证修订值正确 |
| 浏览与质检 | 离线 HTML 展示输入和预期，支持筛选、字段映射、反馈导出；检查空值、ID、重复、表面冲突、长度异常 | 是结构检查与人工阅读辅助，不是语义验真 |

主要证据：[数据准备契约](../skills/atk-dataset/SKILL.md#workflow)、[标准共识模板](local-context.md#recommended-template)、[定向写入实现](../skills/atk-dataset/scripts/update_dataset.py)、[数据浏览契约](../skills/atk-visualize-dataset/SKILL.md)。

这一设计有两个值得保留的选择：不强求所有任务都有唯一“标准答案”；允许先运行可执行输入，把缺乏判断依据的结果保留为 unknown，避免为了填满表格而编造标签。

## 目前如何确定和执行评分

`atk-eval` 主要负责运行 Agent 并保存输出，最终判定在 `atk-diagnose` 完成。

判定依据来自用户要求、样本中的预期字段，以及可选 `.atk/context.md`。显式硬约束用确定性检查，语义要求由当前会话 Codex 判断；稳定规则可按项目生成到 `.atk/runner/failure_rule.py`。模板的 `judge(row)` 仍需实现，不是开箱即用的通用评分函数。

当前规则包括：

- 格式检查通过不能代替任务成功；适用的硬失败不能被整体印象覆盖。
- 规则只覆盖部分要求时，未覆盖部分仍需语义复核；全部适用条件得到支持后才能判 passed。
- 缺证据、歧义、未检查样本保留 unknown；执行错误与业务失败在理由中区分。
- `judgments.csv` 原生契约为 `atk_id,verdict,reason,results_sha256`，其中 verdict 是 passed / failed / unknown。
- `failure_cases.csv` 只包含确认失败；unknown 不进入 `--only-failures`，需要补证据重判或明确选样重跑。
- 报告区分执行、已判定、通过、失败和未知数量；给比率时说明分母，不能把失败数减少直接当作提升。
- 新规则在有已知正负例时，用少量案例检查，但没有固定的校准集或一致性计算流程。

主要证据：[诊断流程第 39–63 行](../skills/atk-diagnose/SKILL.md)、[规则模板第 71–77、94–118 行](../templates/.atk/runner/failure_rule.py.md)、[报告契约第 85–91 行](../skills/atk-report/SKILL.md)。

因此，ATK 当前原生提供的是**带证据的三态判定**。可以在项目规则中编写分数、阈值或指标，也可保留用户自带的列，但尚无统一的多维分数、分档锚点、权重、部分得分及聚合输出契约。对于明确的通过/失败任务，这不构成缺陷；对于主观质量和多目标权衡任务，仅有最终 verdict 难以说明具体改善在哪里。

## 目前不足在哪里

### 1. 标准可以存下来，但形成标准的支持仍较弱

`atk-dataset` 会检查已有标准、询问缺失事实，并复用已确认共识；但尚未形成明确的工作步骤，将业务目标转成“判什么、允许哪些等价结果、哪些条件一票否决、哪些情况暂不判断”，再通过代表样本检查理解是否一致。

例如代码生成任务，可以用构建成功、指定测试通过、禁止路径未改等条件定义成功，无需准备唯一参考代码。ATK 的 `acceptance_criteria` 能表达这种需求，但具体选择哪些可验证条件、如何读取对应产物证据，仍由本次操作者临场设计。

### 2. 答案存在、已被审阅、依据可信尚未被区分

数据集会保留用户提供的任意列，因此可以承载来源和复核信息；默认契约却没有逐样本的来源、依据定位、待审/确认/争议状态及确认人。

数据浏览页所谓 ground truth confirmation，实际是展示预期并收集异常自由文本。导出仅含 `atk_id,row_number,review_feedback`，只导出非空反馈。没有反馈无法区分“已看过且正确”与“未看过”。也没有多人标注分歧处理或一致性统计；对于个人小规模使用，后者未必需要立即建设，但已审与未审的区分直接影响可信覆盖率。

证据：[浏览器 app.js 第 557–590、676–735 行](../agent_tune_kit/visualize/assets/dataset/app.js)、[本地 context 边界](local-context.md)。

### 3. 校准裁判的支持不足

当前只要求有已知正负例时检查新规则；尚未固定一组人工认可的正例、反例、边界例和应判 unknown 的例子，来检验规则与语义裁判是否执行了同一套标准。

因此现有测试能证明文件生成正确、未知不会误算通过，却不能回答裁判会漏掉多少失败、误杀多少正确回答、对相同输出重复判断是否稳定。尤其答案整理与语义判断都可能由同一类模型完成，需要外部权威资料或人工锚点避免重复同一种误解。

证据：[atk-diagnose 第 55–57 行](../skills/atk-diagnose/SKILL.md)、[测试中注入 expected_verdict 的 judge](../tests/test_diagnosis.py)。

### 4. 结果有版本，判定标准尚未完整绑定版本

已有的实质保障是：runner 将执行时的输入、预期字段和输出写入本轮结果；judgment 绑定结果 CSV 的 SHA-256；历史结果不因后来修改答案而自动重写。浏览器也会检查判定的 ID、理由、verdict 和哈希。

缺口是该哈希不绑定 `.atk/context.md`、规则代码、语义裁判提示词/模型或评分方案版本。对同一轮重新判定会替换 judgment，没有独立的判定历史。因此“结果没被改过”不等于“标准没变、裁判可复现”。

报告 Skill 明确要求检查跨轮标准与样本可比性，优化 Skill 也禁止修改 Ground Truth Standard 来制造通过。这些约束目前主要由 Codex 执行，尚不是固定程序门禁。

证据：[结果保留源字段](../templates/.atk/runner/eval_runner.py.md)、[judgment 哈希验证](../skills/atk-visualize-failures/scripts/generate_failure_browser.py)、[报告第 51 行](../skills/atk-report/SKILL.md)、[优化第 38–41 行](../skills/atk-optimize/SKILL.md)。

### 5. 代表性与回归保护仍靠使用者组织

Skill 提醒选常见成功、已知失败和边界样本；报告也提醒 failure-only 的结果不能代表全量改善。但未发现固定的优化集/保护集划分、按业务切片的覆盖目标或自动全量回归门槛。

这意味着一个小失败集可以支持定位修复，却不能单独说明整体业务效果提高。是否需要独立保护集及如何划分，应由实际任务的泛化要求决定。

## 两处与这些边界直接相关的实现细节

1. **反馈来源校验依赖 Skill。** Skill 要求确认导出属于本数据集，不可只靠 ID 或时间戳；helper 的缺省发现逻辑仍会选择 Downloads 中最新且 ID 可匹配的文件。导出缺少数据集身份或内容摘要，因此不同项目的相同 ID 无法由脚本区分。正常遵守 Skill、传入已核对的显式路径可以降低这一风险。
2. **验收条件列的默认浏览体验未完全贯通。** 写回支持 `acceptance_criteria`，但浏览器自动识别预期列的候选未包含它；用户可手动切换，切换后却不会重算 Python 生成时固化的质量标签。不能将这些标签理解为所有验收字段都已得到检查。

证据：[update_dataset.py 第 126–158 行](../skills/atk-dataset/scripts/update_dataset.py)、[expected 候选及 lint](../skills/atk-visualize-dataset/scripts/generate_dataset_browser.py)、[字段切换第 1026–1044 行](../agent_tune_kit/visualize/assets/dataset/app.js)。

另做了一个临时合成检查：v1/v2 使用相同 `atk_id`、不同 `expected`，v2 写入合法的 passed 与本轮结果哈希；失败浏览器仍将旧目标标为 `resolved`。该状态说明当前裁判认为此 ID 通过，不能自动证明标准未变。**这不等于 atk-report 一定会误报提升**：报告另有检查可比性的指令，只是程序尚未强制该检查。相关实现为 `generate_failure_browser.py` 的 `read_judgments`（第 448 行）和目标状态计算（第 659 行附近）。

## 是否足够：按使用目标判断

| 使用目标 | 判断 | 条件或缺口 |
|---|---|---|
| 少量、标准明确的样本，开发者逐条看结果 | 基本够用 | 开发者能够确认预期和判定依据 |
| 参考答案不唯一，但验收条件清楚 | 可用，仍需项目化设计 | 自然语言 criteria 已支持；规则与证据检查需要按任务生成 |
| 从模糊业务要求建立第一版可信数据集 | 支持不够完整 | 标准形成、来源定位、审阅状态仍缺固定工作步骤 |
| 文本质量、工具决策等主观或多维评价 | 支持偏弱 | 缺分档锚点、逐维判定和裁判校准证据 |
| 长期自动调优、跨轮量化证明提升 | 还不够 | 需冻结标准和裁判身份，控制数据变化，补回归保护 |

## 最小改进建议（未实施）

优先补全现有 `atk-dataset` 与 `atk-diagnose` 的工作，不必先增加 Skill 数量或建设通用标注平台。

1. **在 atk-dataset 中补“形成标准”的步骤。** 根据代表样本提出可审阅的标准：正确结果的表达方式、可信来源、必须满足、允许变化、硬失败、缺证据处理。只把需要领域判断的分歧交给用户；已有明确标准直接复用。将逐样本的依据与审阅状态和项目级共识分开，允许复用现有字段，不强制统一所有业务数据 Schema。
2. **在 atk-diagnose 中补最小裁判校准。** 为新标准选择少量人工确认的正例、反例、边界例和 unknown 例，比较预期判定与裁判输出，暴露误通过/误失败及分歧原因。仅在业务确实需要时加入维度和分档，不默认引入总分及权重。
3. **把本轮标准和裁判依据与结果绑定。** 在结果证据中保留适用的标准版本或内容摘要、规则实现及语义裁判信息，比较前识别标准/输入变化；必要时在同一套标准下重评新旧输出。若仅缺判断证据，先重判已有输出，不默认重跑昂贵 Agent。

前两项直接减少确定 ground truth 和评分方案的负担，第三项防止后续调优结论失真。反馈导出身份、已审/未审表达及 criteria 列识别，可以作为贯通前两项的具体修补。

业务成功边界、权威资料选择、硬失败条件和误判代价仍需用户或领域负责人确认。ATK 可以承担整理证据、提出选项、集中暴露分歧和核验一致性的工作，不能仅凭生成一份答案或评分规则替代这些判断。

- [数据校验](../agent_tune_kit/datasets/validation.py) 主要验证 ID，没有真值来源与确认有效性契约。
- [反馈读取](../agent_tune_kit/datasets/updates.py) 仍接受三列反馈并按 ID 匹配；缺少针对原始内容的检查。
- [数据浏览器](../agent_tune_kit/visualize/assets/dataset/app.js) 把“有反馈”计为已审；尚无独立的“当前答案已核对正确”。
- [比较函数](../agent_tune_kit/results/summary.py) 明确返回 `comparability_requires_review=True`，尚未计算标准是否相同。
- [判定保存](../agent_tune_kit/results/judgments.py) 最终只写四个 `JUDGMENT_FIELDS`；往临时 CSV 随手增加标准或裁判列，并不能使其自动保存在 judgments 中。

### 第一优先级：把答案形成与复核做成完整流程

先完善 `atk-dataset` 的工作步骤，使它能帮助用户确定真值，而不只是等待用户提供答案：

1. 从已有资料和代表样本识别需要判定的目标，区分精确值、可接受结果集合、行为/产物验收条件。
2. 找到支持结论的依据，定位到文件章节、记录或用户明确制定的业务约定；说明依据如何支持答案，暴露缺失信息和冲突。
3. 提出“必须满足、允许变化、硬失败、何时未知”的标准草案，用少量成功、失败和边界样例核对理解。
4. 把资料可直接确定的内容整理好，只将真正的业务取舍和分歧交给用户；已经确认的标准无需每次重新询问。
5. 保存有范围的复核结论。模型生成的候选、模型自检通过、答案非空都不能自动视为人工确认。

执行型 Agent 应优先判断最终状态和必要的过程约束。例如修改配置任务，可以把指定配置值、构建结果、禁止修改路径作为验收条件；不必编造唯一参考代码或强制唯一工具调用顺序。这里仍由 Skill 和项目规则确定实际要检查的产物，CLI 不内置领域答案。

对依据明确、可被稳定验证器检查的样本，可以按用户已确认的准入规则批量验证；不要求所有样本逐条人工点击。主观取舍、冲突和缺依据的样本才是重点复核对象。

### 最小可信度契约

先规定记录必须表达什么，再确定字段名。继续使用原来的 `expected`、`label`、`acceptance_criteria`，不复制一套答案。

| 信息 | 应表达的内容 | 由谁负责 |
|---|---|---|
| 确认对象 | 样本 ID、实际答案字段或字段组、适用输入和上下文 | Skill 明确语义；模块验证引用存在 |
| 判断依据 | 可定位来源、版本/日期，必要摘录或推导说明；也可以是明确的人工业务裁决 | Skill 整理、用户或可信验证器核实 |
| 复核决定 | 待复核、已确认、有争议；谁/以何种依据/何时确认 | 明确的复核动作提供，模块记录并校验结构 |
| 内容绑定 | 这次确认针对的输入、答案、相关标准和依据版本的摘要 | 模块计算与复验，失配派生“已过期” |

可先在现有 `dataset.csv` 按需增加一个 ATK 保留的结构化元数据列，按实际答案字段记录上述信息；列名可在实现规格中确定。这样能兼容多答案字段，避免引入新的数据库、manifest 或第二份数据集。必须明确排除该列进入 Agent 输入。

几个不可省略的规则：

- **确认必须有范围。** 确认了 `label`，不能自动认为同一行的 `acceptance_criteria` 也已确认。
- **修改答案不继承原确认。** 用户反馈“补一句说明”并不等于确认了模型后来生成的整段文字；明确给定并批准的替换内容可以直接记录对应确认。
- **过期状态从内容比较得出。** 不只在 update 时清状态；手工编辑 CSV、覆盖导入或标准变化后，inspect/diagnose 也要识别过期。无关字段修改不应让确认失效。
- **不要给整个 context.md 做一刀切的标准哈希。** 只绑定适用的标准条款或明确版本，避免新增普通调优记录使所有样本失效。
- **反馈携带数据集来源、目标字段和原始内容摘要。** 同批反馈对同一更新前快照验证后再一次写入；旧导出、跨项目重号、陈旧 localStorage 不能直接变成有效确认。
- **hash 只证明针对同样内容。** 它不能证明来源权威、推导正确或审阅者确实审阅过。URL 可定位，但若内容会变，还需要版本或保留必要证据。

沿现有 `dataset inspect/update` 完成检查和应用；答案、依据和复核记录应在同一次 CSV 原子写入中更新，避免要求 Skill 分三次改文件并自行维持一致性。`prepare` 负责保留并检查导入记录，不能因为数据来自已有 CSV 就自动视为可信。

### 第二优先级：让可信状态真正影响诊断与报告

维护两个独立问题：**依据是否足以支持这个判断**，以及 **Agent 的结果是否通过**。

| 情况 | 应有处理 |
|---|---|
| 依赖的参考答案待复核、有争议或过期 | 该正确性要求不能据此确定通过或失败；缺其他依据时为 unknown |
| 无参考答案，但独立、已确认的硬约束被明确违反 | 仍可判 failed，写明约束与证据 |
| 只有 JSON 格式检查通过，业务要求未覆盖 | 不能判整体 passed |
| 裁判执行失败或校准暴露分歧 | 这是判定证据不足，不能自动变成 Agent 业务失败 |
| 所有适用条件均有有效依据且满足 | 才能判整体 passed |

共享模块检查引用的真值/标准状态、内容绑定和必填证据；是否真正覆盖业务条件仍需要 Skill 或项目规则判断。只增加一个 `confirmed=true` 不能让 CLI 自动理解业务。

`results inspect` 和报告应分别展示复核覆盖、可判定范围、判定覆盖、通过/失败/未知及原因。旧数据继续可执行、可浏览，历史判定保留；缺少新增证据时标明可信性未记录，不将它自动提升成经过可信度验证的验收结论，也不默默改写历史 verdict。

### 第三优先级：固定评分标准，并校准裁判

先复用现有 `.atk/context.md` 中的标准，补足每项要求的适用范围、正反例、硬失败、允许变化及所需证据；明确哪些能用规则检查、哪些需要语义判断。必要时保留逐条件判断；业务确实需要等级、部分得分或权重时再加入，不先建设通用打分引擎。

建立一小组人工认可的“输入＋待判输出＋期望判定及理由”，覆盖正确、错误、边界和证据不足。这是校准裁判的数据，不能仅拿 Agent 优化失败集当作充分的校准证据。

- `atk-diagnose` 选择校准例、解释分歧，并检查规则覆盖的标准。
- 确定性裁判复用 `execution/rules.py` 的 judge 执行逻辑；校准调用应允许只返回结果，不覆盖正式轮次的 judgment/failure 文件。
- 语义裁判继续由 Skill 执行，不新增强制 LLM 调用层；已获得的判断交给固定代码做匹配与统计。
- 固定代码统计误通过、误失败、未知和分歧 ID。合格标准由业务误判代价决定，不发明统一百分比。
- 规则或适用标准改变时重新校准；模型/判定方式变化时说明原校准是否仍适用。相同稳定条件下无需每轮重复审批。

仅有几个案例通过可作为起步证据，不能据此声称裁判对所有场景都准确。对主观判定可在这组样本上检查重复判断一致性；保留可获得的裁判信息，无法读取的模型版本明确未知。

### 第四优先级：让跨轮比较有可检查的依据

扩展 `results/judgments.py` 的正式保存契约，绑定本次判定实际使用的标准内容或不可变引用、裁判方法、规则实现及校准依据。仍可使用现有 `judgments.csv` 的保留元数据列；不能仅在传入 CSV 中加列而不改写入契约。

注意两件事：

1. 标准哈希用于检测变化；复现旧判定还需要标准内容快照或可恢复的不可变版本。仅保存当前路径加哈希不够。
2. 将运行时保存的样本/真值信息与判断时实际使用的标准分开。标准后来修订时，可能只需重新判断两轮已有输出，无需重新调用 Agent。

`results compare` 在明确字段映射后，比较目标样本输入、预期/验收条件、标准及裁判信息，返回变化项和缺失项。程序发现不同就限制直接声称改善；Skill 判断是等价表达、标准修订还是实验条件变化，并决定是否需要在同一标准下重评。

当前轮 passed 事实可以保留，但不能自动推出 Agent 调优导致改善。历史判断不能被静默覆盖；重新判定应保留原判断及重判依据。裁判信息一致也只解决部分可比性，Agent 模型、工具、运行环境和样本选择仍需要对应的实验控制。

### 实施顺序与验收

建议按完整使用流程逐步交付，先完成第一行，再扩大范围：

| 顺序 | 交付内容 | 可判定的完成标准 |
|---|---|---|
| 1 | 依据 → 有范围的确认 → 内容变化失效 → 诊断消费 | 能解释一个答案为何可信；确认 label 不影响其他字段；旧反馈不能套到新输入/答案；受影响结论保留未知 |
| 2 | 小型裁判校准 | 固定输出样例的预期判定能复验；误判和未知可见；不运行被测 Agent、不覆盖正式结果 |
| 3 | 标准与裁判绑定、可比性检查 | 标准变化能检出，历史标准可恢复；数据修订不会被自动报告为 Agent 提升 |

第一步涉及 `datasets`、现有数据浏览页、`atk-dataset`、诊断读取及报告统计；验收至少覆盖：多答案字段、手工改 CSV、标准变更、旧反馈与跨项目重号、无变化写入、旧格式读取，以及新增元数据不泄漏给 Agent。无需先引入新 Skill、后台服务或多标注员平台。

新增元数据和反馈字段属于明确的契约扩展。旧三列反馈可继续用于解释性修订，但不能凭缺少快照的导出证明复核仍有效；保留旧格式读取能力，同时说明新版可信结论需要哪些证据。

### 与执行现场方案的衔接

[执行现场与调用轨迹方案](execution-evidence-and-tracing-plan.md) 已规划把运行时样本、标准和相关文件保存到 `.atk/results/vN/executions/<execution_id>/context/`，该方案仍待实施。如果两项能力共同落地，应复用这一执行时快照及引用规则，不另外生成一套平行的运行标准档案。

这里仍需区分：

- `dataset.csv` 和 `.atk/context.md` 是后续工作使用的当前资产；修订它们不改历史现场。
- 执行时快照说明运行时使用了什么；它不能替后来修改的评分标准背书。
- 诊断时采用的新标准必须由该次判定绑定，不能塞回或覆盖已封存的执行现场。
- 原资料仍是业务事实来源，样本中的引用与快照只保留本次判断所需的依据；拥有一份快照不意味着该资料天然权威。

若尚未实施执行现场方案，可信度第一阶段仍可独立完成；不要把完整轨迹采集变成填写来源和有效复核的前置条件。第三阶段的历史复验则必须另有可取得的标准内容或不可变版本，只有当前路径和哈希不够。

### 用户如何使用

保留现有 Skill 入口，不要求新增一组 ground truth 命令。下面是完成增强后的预期体验，不是当前版本已具备的行为：

| 时机 | 用户动作 | 系统新增工作 | 用户少做的事 |
|---|---|---|---|
| 首次准备 | 向 `$atk-dataset` 提供业务资料和代表样本 | 提出验收标准、候选预期、依据和待裁决问题；记录确认范围 | 不必从空表开始手写所有答案与评分规则 |
| 复核样本 | 在对话中确认指定范围，或可选使用 `$atk-visualize-dataset` | 同时展示依据，支持确认正确或标为争议；验证反馈对应的内容 | 不必为了表达“正确”而编写修正意见，也不必强制导出反馈 |
| 批量执行 | 继续 `$atk-init`（需要接入时）和 `$atk-eval` | 保存当次样本与真值信息；确保这些信息不泄漏到 Agent 输入 | 不必每轮手工拷贝标准和核对数据版本 |
| 诊断 | 继续 `$atk-diagnose` | 先检查判断依据是否有效；阶段 2 在适用标准/裁判变化时校准，再完成判定 | 不必自己重复检查过期确认、拼接来源或计算分歧 |
| 读报告 | 继续 `$atk-report` | 说明哪些确实失败、哪些无法判断、哪些因为标准或裁判改变不可直接比较 | 不必从失败数量变化自行猜测是否进步 |
| 修改答案/标准 | 继续向 `$atk-dataset` 描述修订 | 找出受影响的确认和判断，保留旧结果，要求相应复核或同标准重判 | 无关样本无需全部重审，缺判定依据时不默认重跑 Agent |

用户新增的主要工作集中在第一次确定业务边界、确认有争议的真值，以及校准裁判的代表样例。用户明确确认过的范围可批量记录；稳定规则能验证的内容按已确认约定处理。后续重点处理变化和分歧，不把每轮逐条确认设为固定仪式。

### 差异主要出现在哪些地方

| 观察点 | 目前 | 预期增强后 |
|---|---|---|
| 一条样本 | 可以看到输入和预期文本 | 还能说明预期依据、确认范围，以及确认是否仍有效 |
| 浏览器中的“已审” | 目前主要按是否填写反馈推断 | 明确区分写过反馈、确认正确、有争议与未复核 |
| 修改一个答案 | 主要保证改对行、保留其他字段 | 同时重新判断原确认的有效性，拒绝陈旧反馈直接套用 |
| 一个 verdict | 有理由和结果哈希 | 能定位适用标准和有效依据；明确未判定的原因 |
| 一组评分规则 | 能运行并产出 verdict | 有代表样例上的校准证据，能看见误通过与误失败 |
| 跨轮“已解决” | 主要依赖 Skill 审阅可比性 | 固定代码提供内容/标准/裁判变化证据，报告区分观察到的通过和可归因改善 |
| 日常操作 | 使用既有 Skill/CLI | 入口基本延续，页面信息、异常提示、检查和报告更完整 |

示例：某样本的预期是“输出必须包含 A、B，可省略 C”，依据为已确认的规则 R1。用户确认该输入和预期后，系统保存对应内容绑定。后来规则改为 R2，要求必须包含 C，旧样本仍保留 R1 下的历史判定；新判断会提示适用标准已变化。只有按 R2 补齐样本依据并重新判读后，才能给出 R2 下的结论，不能把单纯修改标准当成 Agent 提升。

一个示意报告可分别写：20 条样本均执行，其中 16 条参考依据有效、4 条待复核；有效依据组中 12 通过、3 失败、1 条因输出证据不足未判定。若这批样本均需参考依据且没有独立硬失败，则总计 12 通过、3 失败、5 未判定。复核覆盖为 16/20，判定覆盖为 15/20；若给“已判定样本通过率”，应明确为 12/15，不能省略另外 5 条未知。这些数字只是说明展示方式，不是实际评测结果。
